# Auto Compact 综合审查与定稿建议

状态：审查意见与修订建议，尚未实施。本文不宣称拟议命令、Mod 或维护账户已经存在。

## 2. 需要补齐的高优先级契约

### R1：明确谁负责建立原生 idle 设置，P1

位置：原设计 §9、§13；`lib/terminal.mjs:80`、`:277`。

**场景**：用户启用自动维护并 adopt 一个已运行的 Claude，会话仍启用原生 idle
compaction。登记会话不能追溯修改启动参数；如果没有明确的激活流程，自定义 57 分钟
策略可能一直停在观察态，或与约 54 分钟的原生 idle 行为冲突。

采纳 Kimi 对启动绑定不完整的意见，但不采纳「所有 adopt 会话永远只能观察」的结论。
如果已运行会话的有效设置已经是 `idleCompaction:false`，其他能力与宿主准入条件也
满足，可以激活；否则只观察并明确说明原因。

定稿需选择并落实两条路径：

1. 受管启动：扩展现有 terminal/backend 边界，生成仅供本次会话使用的 settings
   覆盖，明确 argv 合并点、文件哈希和所有权。既有用户参数不能被字符串拼接覆盖。
2. 既有会话：校验实际合并设置与能力，不尝试热注入启动参数。没有可靠证明就不激活。

不关闭 `autoCompactEnabled`，不改写全局 Claude 设置，不新建第二套终端执行器。
Mod 缺失、停用或 CLI 故障后，必须显示自动维护未运行；不能宣称已自动恢复启动时
被关闭的原生 idle 行为。若需要会话内热回退，必须先验证真实原生接口支持它。

### R2：把 Mod 与 CLI 的往返写成协议，P1

位置：原设计 §3、§6、§8；Kimi P1-5。

**场景**：到点评估后，Mod 等待 CLI 准入。期间用户提交输入、缓存窗口结束，或 CLI
已经写入声明但调用方超时。仅写「提交前再检查」不足以判断哪些额度可以回收、旧 token
是否还能使用、是否可能再调用一次原生压缩。

建议采用短命 CLI 进程与结构化 JSON 请求/响应，不增加守护进程或 HTTP 服务。
拟议操作为 `register`、`observe`、`claim`、`consume`、`finish`、`status`；均由
`bin/omha.mjs` 验证，不是当前已有的 CLI 命令。

请求仅包含会话身份、输入/业务/缓存版本、策略哈希和最小观察元数据。使用 argv 数组
传递有界 JSON，禁止拼 shell 字符串。响应要求单个合法 JSON envelope，诊断走 stderr。
本地 RPC 默认截止时间建议 2 秒，同时受剩余缓存窗口约束。

`claim` 产生短期、一次性的 PREPARED 声明；`consume` 在宿主锁下重新检查版本和窗口，
持久化 INVOCATION_INTENT 后才允许原生调用。Mod 还需检查其本地最新输入版本；原生
API 的忙碌拒绝与队列优先级必须通过目标版本探测。

`prompt.submit` 关键路径先在进程内撤销 timer 和未提交意图，不阻塞等待 CLI。新的
inputRevision 在本地立即生效，异步宿主同步失败时关闭自动执行，而不是放宽版本检查。

### R3：增加持久的原生会话维护账户，P1

位置：原设计 §11；`lib/runner.mjs:93`、`:188`、`:218`。

**场景**：每次 Mod 调用都启动一个 CLI 进程，运行时账户重新初始化；如果直接使用
进程内 `ProviderRuntime.account`，「每会话最多 8 次」可能被重启绕过。

现有 reserve/settle 的准入与未知费用语义可以复用，但持久会话账户不是现成能力。
需要将账户、活动预留、调用意图和结算写入同一个可重放账本，并复用现有锁与原子存储。

维护账户以稳定的 provider/nativeSessionId 标识为核心，项目与 profile 作为绑定和预算
维度。不能通过 resume、Mod 重载、`/clear` 或对话 epoch 更换清零同一真实会话的维护
总次数。业务去重键仍包含 conversationEpoch，与预算键分开。

**不采纳 Kimi「无法映射 profile 时零预留、仅计次数放行」的默认降级。**
无法建立有效预算绑定就拒绝准入。只有独立、明确配置的宿主预算策略才可以只约束次数，
不能将映射失败自动解释为获得豁免。未知 usage 保留预留，不伪造美元成本或 cache saving。

### R4：规定执行意图、不确定提交和回收条件，P1

位置：原设计 §10、§11；Kimi P1-5 的超时建议需要修正。

**场景**：consume 已持久化调用意图，但响应丢失或 Mod 随后崩溃。仅凭「RPC 超时」
无法证明原生调用没有发生，不能直接返还额度并让新进程再执行一次。

建议区分：

| 状态                       | 是否允许回收或重发                                    |
| -------------------------- | ----------------------------------------------------- |
| PREPARED，尚未消费         | 经宿主确认 token 已撤销、没有消费记录后可释放活动预留 |
| INVOCATION_INTENT 已持久化 | 计一次维护尝试；未确认副作用前不释放、不重发          |
| 明确的未派发拒绝           | 只有目标版本契约能证明尚未调用摘要请求，才按规则结清  |
| 已应用压缩                 | 保存原生边界，推进压缩版本，等待新业务                |
| 执行结果不确定             | 从权威边界与活动状态核对；缺少证据则保持未结清        |

这沿用原设计对 uncertain writes 的保守处理，不承诺无法证明的跨进程 exactly-once。
也不能为追求自动恢复而把未知请求静默改成失败并重新提交。

### R5：将执行结果未知与费用未知分开，P1，综合复核补充

位置：原设计 §10、§11 的 unknown 分支。

**场景**：原生 API 已明确返回压缩完成，但没有返回 usage。如果把这两种未知合并成
一个阻塞状态，会让后续业务永远无法重新启用维护；反之，知道 usage 也不能证明压缩
已经应用。

建议记录两个正交维度：

- 执行：prepared、intent、in-flight、applied、skipped、failed、execution-unknown。
- 记账：reserved、settled、usage-unknown。

只有执行未结清才阻止新的自动压缩。费用未知保持预留，但在执行已确认且剩余预算足够
时，不必永久阻塞后续新业务版本。恢复判断不能用新的用户消息替代旧操作的完成证据。

### 已补充的官方事实

官方缓存文档明确写明：每次命中缓存会重置计时。API 文档也明确 TTL 从读或写缓存的
**请求起点**计时，不从回答结束计时。因此不采纳原报告将基准改成「最近写缓存请求
完成时刻」的建议，这既忽略读续期，也会把长响应时间额外算进有效期。

官方 Mods 类型中，`$.session.compact()` 被描述为与 `/compact` 相同的会话压缩调用，
忙碌时拒绝；`next(e)` 返回压缩结果或 skip。已查到的快照头部为 2.1.277，不能因此
推断目标版本一定相同，但「未查到」也不能等同于「不存在」。

完成证据应按版本适配器定义权威来源：本次调用的可验证成功结果可确认执行；外部
手动/原生压缩通过原生完成边界或 PostCompact 确认。有多个来源时检查一致性，冲突
转 unknown；不要求无条件同时等待两个可能不同时出现的事件。

## 4. 建议冻结的完整方案

### 4.1 配置

继续扩展现有配置发现链，字段是 root-level `maintenance.autoCompact`，校验应修改
`validateProfiles` 的顶层 allowlist 和对应 schema，不是 per-profile allowlist。

```json
{
  "maintenance": {
    "autoCompact": {
      "enabled": false,
      "afterMinutes": 57,
      "minContextPercent": 20,
      "minIntervalMinutes": 10,
      "minRemainingSeconds": 30,
      "maxCompactionsPerSession": 8,
      "bridgeStatusLine": false
    }
  }
}
```

维持原有范围和联合校验。新增 bridge 开关只授权数据桥接，不授权覆盖已有状态栏、
改变全局设置、使用 API 预热或降低其他执行条件。

### 4.2 激活与能力

先验证 Mod、CLI、原生 API、缓存字段、预算和所有权，再建立本次会话的维护绑定。
新受管会话使用临时 settings 覆盖；既有会话读取实际有效设置，满足同样条件即可加入。

状态明确区分 disabled、unsupported、observation-only、ready、active、unavailable。
本机 2.1.220 只能保留普通 skills 和 CLI 历史状态，不提供实时 Mod 观察或自动压缩。
不自动升级 CLI、不启用全权限模式，也不关闭正常上下文超限恢复。

### 4.3 数据观察与门槛

上下文优先使用 `context.tokens/window`，以原始计数比较 20% 边界。小于阈值不触发，
等于阈值仅允许继续检查其他条件。刚压缩后的未知测量不能用旧值代替。

缓存优先使用目标版本真实的结构化字段；`$.session.usage()` 没有承诺的字段不能臆造。
必要时显式开启状态栏桥接，保存原有脚本的输入输出与退出行为；没有现有状态栏时，
还需说明新增状态栏可能改变 footer 提示。无可用证据则不执行，不读屏幕猜缓存。

窗口公式不变：一小时 TTL 时 `dueAt = expiresAt - 3 分钟`，默认最晚发起点为
`expiresAt - 30 秒`。以实际请求对应的证据为准；预计 warm 不是实际 cache hit 保证。

### 4.4 输入接受与 53 分钟重排

输入接受后立即递增 inputRevision，取消旧 timer 和未消费声明。此时只暂停旧计划，
不伪造缓存刷新，不推进 workRevision，不解除连续 compact 保护。

新请求产生有效缓存证据且覆盖当前待处理输入后，才计算新 dueAt。每个回调、声明和
缓存快照携带输入/业务/缓存版本与策略哈希；旧回调即使已经排队也不能通过最终校验。

```text
10:00:00  缓存刷新，原计划 10:57:00
10:53:00  新指令被接受，立即撤销旧计划
10:53:20  对应请求读写缓存，预计 11:53:20 到期
10:58:00  回答完成，不把 TTL 基准改成回答结束
11:50:20  新的评估时间；仍需满足 20%、空闲、去重与预算条件
```

请求取消或失败且没有刷新证据时，不恢复旧任务、不凭输入延长 TTL。第 53 分钟以后、
压缩实际提交之前的新输入采用相同规则；53 不是新的硬截止线。

### 4.5 调度与状态机

每个有效 cacheEpoch 只维护到点评估和最晚发起点两个单次 timer。到点忙碌则进入
Deferred，依靠活动完成事件重新评估；无论活动事件是否出现，最晚发起点 timer 都
让它过期退出。若保留额外重检，应有界，但不能用重检次数代替绝对截止时间。

```text
Observing -> Armed -> Due -> Prepared -> InvocationIntent -> Applied
                   -> Deferred -> Due
                   -> Expired
新输入：Armed / Due / Deferred / Prepared -> AwaitingRefresh
Applied -> WaitingForNewBusiness
InvocationIntent / InFlight -> ExecutionUnknown（必须结清后才能再次执行）
```

任意未提交状态遇到新输入、策略变化、会话切换或缓存周期变化，旧 token 失效。
休眠恢复、时钟明显跳变和热重载都先重建证据；过期不补发。

### 4.6 去重与原生协调

保留 workRevision 与 lastCompactedWorkRevision。任意来源完成压缩都推进边界；没有
新业务，即使摘要仍达 35% 也不再次自动压缩。状态查询、心跳和重载不增加业务版本。

预计算摘要单独记录是否仍覆盖当前业务版本；不能把预计算当成已应用压缩，也不能为
相同历史另起一份摘要。原生必要恢复和用户显式手动操作保留优先级。

只有一个缓存到期前维护执行者。Omha 模式需要确认原生 idle 已关闭；不能同时启用
54 分钟原生策略与 57 分钟自定义策略，也不通过禁用全部 auto compact 达成互斥。

### 4.7 执行、确认与恢复

通过 R2 协议取得并消费声明，再调用当前会话原生 `$.session.compact()`。不向模型发送
文本 `/compact`，不模拟按键，不新建 headless provider 进程。

执行前检查最新版本、剩余窗口和活动状态。确认来源必须绑定本次调用或原生边界，
不是 stdout 内容、已送达消息或退出码。skip、明确未派发、失败和未知分别记账。

重载与 resume 不重置账户或去重记录。执行未知不盲目重发；执行已确认但费用未知时
保留预留，不把它误当成仍有一个未完成的摘要请求。

### 4.8 审计与用户状态

继续使用现有原子存储、锁和追加事件。仅保存元数据、版本、哈希、请求/实际模型来源、
维护次数、预留与完成边界，不复制原始对话、工具输出或摘要。

状态显示下一次评估时间、输入等待、缓存/上下文证据来源、native/omha 执行者、活动
预留与最近终态。等待新请求证据时显示 pending，不继续显示已撤销的旧时间。

## 5. 实施与验收意见

### 先完成的探测

1. 在支持版本上生成真实类型，验证 timer、compact 返回、skip、忙碌拒绝、输入队列
   优先级和原生/Mod 并发互斥。旧版本通过格式校验不能代替这些验证。
2. 确认缓存字段获取路径，以及 expires_at 如何绑定具体主请求；验证纯 cache read
   命中后快照更新，遵守已知 TTL 契约，不重定义协议语义。
3. 验证本次会话 settings 的合并和失效范围；核对既有用户参数、多版本 CLI 和原生
   fork 的设置继承，不隐式更改模型、权限或计费渠道。
4. 为声明/账户的持久化、消费、RPC 响应丢失、完成证据缺失建立可重放协议 fixture。

### 必须进入离线矩阵的组合场景

| 场景                                         | 验收重点                                |
| -------------------------------------------- | --------------------------------------- |
| 56:59、57:00、19.99%、恰好 20%               | 时间与原始 token 边界                   |
| 53 分钟输入、响应延迟、请求排队或失败        | 立即撤销、实际请求重排、不凭输入续期    |
| timer 已排队后收到输入、RPC 往返期间收到输入 | 本地与宿主版本检查都生效                |
| Deferred 没有活动事件直到窗口关闭            | 独立到期 timer 保证退出                 |
| 手动、原生、Omha 压缩与预计算交错            | 共同边界、单执行者、无重复摘要          |
| claim 响应丢失、consume 后崩溃、完成日志丢失 | 区分未消费与执行未知，禁止盲目返还/重发 |
| 执行完成但 usage 缺失                        | 保留预留，避免永久阻塞新业务            |
| resume、重载、clear、模型/目录/策略切换      | 不清零真实会话额度，不继承旧 token      |
| 无 CLI、无 Mod、hooks 被禁用、预算未映射     | 明确未运行，skills 仍可用，无零预留降级 |
