Local runtime / provider-neutral / auditable

从用户意图，走到可审计结果。

Omha 把 Claude Code 的提示技能、主机侧验证、模型执行、终端交接和持久化证据串成一条受约束的自动化链路。模型可以提出方案，只有主机可以批准副作用。

02 / capabilities

功能与底层实现

Execution

Provider 路由

根据 profile 选择 Claude、Codex、Kimi、command 或 fake。执行前校验能力、sandbox、超时、环境变量和预算；运行时记录每次 attempt。

lib/profiles.mjs · lib/adapters.mjs · lib/runner.mjs · lib/process.mjs
Planning

Leader DAG

Planner 可以生成任务图，但不能替主机授权。主机验证依赖关系、写入顺序和策略，再由 orchestrator 持久化调度、取消与恢复。

lib/plans.mjs · lib/orchestrator.mjs
Decision

Roundtable 决策

2-3 个独立 voter 只看到公共证据，主机在收齐结果后计算多数或加权票；chair 不能覆盖 host tally，人类门槛需要显式 approve。

lib/roundtable.mjs · schemas/proposal.schema.json
Handoff

终端交接

自动按 cmux → tmux → file 降级。prompt 先写入，资源带 owner token，worker 必须提交认证的完成标记，关闭动作只能作用于自有资源。

lib/backends.mjs · lib/terminal.mjs · lib/handoff-protocol.mjs
Continuation

Native cmux Fork

从已验证的 checkpoint 或 turn 创建 successor，发送结构化续接消息，只有 successor 确认 takeover 后才允许关闭源 surface；不伪造文件恢复。

lib/fork.mjs · lib/session-fork.mjs · lib/terminal.mjs
Parallel work

Open Arena / Session Fork

冻结公共前缀和知识包，运行 2-8 个隔离 lane。所有分支共享预算和 artifact 审计，但不声称复制 provider session 或缓存。

lib/open-arena.mjs · lib/arena.mjs · lib/fork.mjs
Recovery

Automatic Butterfly

监听 host acceptance 失败后的真实重工，要求时间顺序、原始反馈和变更 artifact 同时成立，再触发现有 handoff；hash 变化本身不会触发。

lib/butterfly.mjs · lib/orchestrator.mjs
Maintenance

Native Auto Compact

显式激活后，通过 Claude Mod 事件、cache evidence、context floor 和 durable claim 调度原生 compact。新输入会使旧 timer 失效，未知状态不会冷 replay。

lib/compact.mjs · hooks/controller.mjs · hooks/register.mjs
Knowledge

Scoped Memory

Markdown/frontmatter 是事实源，索引和注入都有行数、字节、freshness 和 scope 上限。hash、锁和 no-follow 写入防止过期或越界覆盖。

lib/frontmatter.mjs · lib/memory.mjs · lib/storage.mjs
Verification

Acceptance / Review

provider 完成、主机验收和独立 review 是三种不同结果。验收冻结 harness 与 artifact hash，review 排除实际作者，失败不会被执行结果覆盖。

lib/orchestrator.mjs · lib/runner.mjs · docs/contracts.md
Observability

Status / Supervision

从 durable events 重放状态，支持 JSONL watch、stall/input-wait 监督和有限只读 takeover。写任务卡住时保持 interrupted，要求显式 replay。

lib/orchestrator.mjs · lib/runner.mjs · bin/omha.mjs
Distribution

Claude Code Plugin

插件只安装 prompt skills 和 opt-in Mod，不自动安装 CLI。技能可在没有 CLI 时继续提供推理，确定性动作仍回到 host validation。

.claude-plugin/ · skills/*/SKILL.md · docs/plugin.md
03 / one request

一次任务如何穿过系统

下面的顺序适用于 Leader、provider 调用和需要验收的写任务；不同生命周期会复用同一套 host boundary。

STEP 01

提出意图

用户或技能提供任务、证据、候选方案和期望结果。这里允许开放式推理，但不产生主机权限。

STEP 02

冻结并验证

CLI 解析 version 1 输入，校验 profile、DAG、policy、预算、所有权、写入模式和证据 hash。

STEP 03

执行并记录

runner 启动被允许的 adapter；orchestrator 写 append-only events，保存 attempt、usage、结果和失败阶段。

STEP 04

验收与恢复

主机运行 acceptance 和独立 review，决定依赖是否释放。崩溃或不确定写入进入可见状态，不会静默重放。

04 / trust model

什么由 Omha 保证

这不是 provider 的安全沙箱。Omha 保证的是本地生命周期的边界、证据和失败处理。

主机可以验证的事

  • 输入契约、未知字段、路径、profile capability 和 fallback 资格。
  • 预算 reservation、provider concurrency、worktree lease 和 owned terminal。
  • 事件日志、attempt provenance、response hash、artifact snapshot 和 policy hash。
  • 验收 harness 是否改变、每条 review criterion 是否通过、依赖是否可以释放。
  • 取消、超时、进程组清理和恢复是否留下不确定状态。

仍然需要外部确认的事

  • provider 实际模型、账单和 CLI 内部权限配置。
  • native provider 隐藏的 prompt/tool 字节和完整缓存生命周期。
  • 同一 OS 用户下恶意进程对本地状态目录的攻击。
  • 项目 acceptance 是否真的代表业务正确性。
  • Windows 上原生进程组监督，以及不支持版本的 Claude Mod 行为。

06 / quick questions

几个容易混淆的点

为什么不让 prompt 直接执行 shell 或 provider？

因为 prompt 是不可信的提议来源。CLI 需要在副作用发生前统一检查 profile、预算、并发、所有权和写入授权，才能让手动调用和自动调用拥有同一条证据链。

为什么 provider 成功退出还不能算任务成功？

退出码只能说明进程结束。Omha 还要验证 provider 输出是否完整、主机 acceptance 是否通过、artifact 是否没有被验收 harness 改写，以及需要时独立 review 是否批准。

为什么 Session Fork 不声称复制上下文缓存？

它只冻结可观察的公共前缀和 usage evidence，并通过同一路由和预算门槛启动隔离分支。provider 内部 KV 或隐藏 prompt 字节不可见，所以缓存命中只能按明确 evidence 记录。
